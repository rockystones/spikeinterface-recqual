Based on what I found in the Plexon documentation and changelogs, here are the key settings and strategies to speed up your batch processing:

**Waveform Limit (`Set WaveformLimit`)**

This is probably the single most impactful setting. If a waveform limit is not specified and a channel contains large numbers of waveforms, sorting can take an unreasonably long time. You can use the `Set WaveformLimit` batch command to cap the number of waveforms used for the sorting step. For valley-seeking sorting, the maximum enforced is 400,000 waveforms for 64-bit OFS and 50,000 for 32-bit. The T-Dist E-M algorithm also supports this limit — it can obey a specified Waveform Limit, finding clusters using a smaller subset and then assigning the remaining spikes into those clusters. If you haven't explicitly set this in your batch files, doing so can dramatically reduce per-channel processing time.

**Use `Set IgnoreSrc` / `Set SuppressOutputSrc`**

The `Set IgnoreSrc` batch command allows skipping over sources during batch operations — for example, if you're re-extracting from continuous data and don't need the original spike source. Similarly, `Set SuppressOutputSrc` allows a source to be processed but not written out to any output files, which saves I/O time if you don't need to export certain wideband data.

**Process Priority Caveat**

Be aware that Offline Sorter running in batch mode will lower its process priority, to allow background sorting while acquiring data on the same machine. If you're not simultaneously acquiring data, this is working against you. You could use Windows Task Manager to manually raise the priority of each OFS instance back to "Normal" or "Above Normal" after launching your batch jobs.

**Use the 64-bit Version and PL2 Format**

If you aren't already, make sure you're running the 64-bit build — it has improved handling of very large continuous data files (over 2 billion samples per channel). Also, OFS reads .PL2 files with single-channel read times up to hundreds or thousands of times faster than .PLX files, so converting to PL2 before batch processing can make a huge difference in file I/O time.

**Separate Max Iterations for E-M Algorithms**

The max iterations for T-Distribution E-M and Standard E-M are now separate settings, since Standard E-M generally performs better with fewer iterations than T-Dist E-M requires. If you're using Standard E-M, lowering the iteration count can save time without hurting quality.

**Other Practical Tips**

Beyond OFS settings, since you're already running multiple instances, make sure your data files are on a fast local SSD rather than a network drive — disk I/O is often the real bottleneck when multiple instances are competing for file access. You might also consider splitting your batch files so each instance processes non-overlapping files, avoiding any file-locking contention.

Here's how to do it:

Open Task Manager with **Ctrl + Shift + Esc**, then go to the **Details** tab (not the Processes tab — the Details tab gives you the actual process-level controls). Look for **OfflineSorterV4.exe** (or OfflineSorterV3.exe if you're on v3). Right-click on it and select **Set priority**, then choose the level you want — **Normal** or **Above Normal** are reasonable choices if OFS has auto-lowered itself to "Below Normal" during batch mode.

You'll need to do this for each running instance separately, since each one is its own process. Also keep in mind that the priority resets every time you launch a new batch job, so you'd need to re-apply it after each launch.

If you want to automate this so you don't have to manually adjust every time, you can use a small PowerShell command after launching your batch jobs:

```powershell
Get-Process OfflineSorterV4 | ForEach-Object { $_.PriorityClass = "Normal" }
```

Or if you want to go a step further, wrap your batch launches in a script that starts OFS and then immediately bumps the priority:

```powershell
Start-Process "C:\Path\To\OfflineSorterV4.exe" -ArgumentList "/batch yourfile.ofsbatch"
Start-Sleep -Seconds 5
Get-Process OfflineSorterV4 | ForEach-Object { $_.PriorityClass = "AboveNormal" }
```

Just be cautious with setting everything to **High** or **Realtime** — if you have many instances all at high priority competing for CPU, it can make your system unresponsive. **Above Normal** is usually the sweet spot.

> Good, I have enough info to give a comprehensive answer about disabling Windows Efficiency Mode for OFS processes.

Unfortunately, Windows 11 does not offer an official supported method to disable Efficiency Mode globally or permanently for a specific application. It's applied dynamically by the OS based on process behavior, so it can re-enable itself. That said, here are your best options, from simplest to most thorough:

**1. Toggle it off per-process in Task Manager (temporary)**

Open Task Manager, go to the **Processes** tab, find OfflineSorterV4.exe (look for the green leaf icon indicating Efficiency Mode is active), right-click it, and select **Efficiency mode** to toggle it off. This change is temporary and only lasts for that session — it must be repeated each time the process restarts.

**2. Disable Power Throttling via the Registry (system-wide)**

This targets the underlying mechanism that Efficiency Mode relies on. Open the Registry Editor, navigate to `HKEY_LOCAL_MACHINE\SYSTEM\CurrentControlSet\Control\Power`, right-click on the right side, create a New DWORD (32-bit) value named **PowerThrottlingOff** and set it to **1**. Reboot afterward. This tells Windows not to throttle background processes. Note that this isn't an official configuration and might be changed or ignored by future Windows updates, and could increase power consumption.

**3. Set your power plan to Best Performance**

Go to **Settings → System → Power & Battery** and set the power mode to **Best Performance**. This won't fully prevent Efficiency Mode but reduces how aggressively Windows throttles things.

**4. Automate disabling it with a script**

Since OFS batch mode auto-lowers its own process priority (which can trigger Windows to apply Efficiency Mode on top of that), you can run a PowerShell script that periodically resets priority and disables Efficiency Mode via the process API:

```powershell
# Run this in a loop while your batch jobs are active
while ($true) {
    Get-Process OfflineSorterV4 -ErrorAction SilentlyContinue | ForEach-Object {
        $_.PriorityClass = "Normal"
    }
    Start-Sleep -Seconds 30
}
```

This won't directly toggle the Efficiency Mode flag, but keeping the priority at Normal helps prevent Windows from deciding to throttle the process. For actually clearing the EcoQoS flag programmatically you'd need a small C# or C++ utility that calls `SetProcessInformation` with `ProcessPowerThrottling` — that's more involved but is the only truly reliable per-process method.

**Practical recommendation for your OFS workflow:** The registry approach (option 2) combined with manually bumping OFS priority after launch (from my earlier suggestion) is probably the most effective combination. If you're running a dedicated workstation for batch sorting and don't care about power savings, the registry tweak is the way to go.

This is a great question that gets at a fundamental architectural issue with Utah array data. Let me break this down comprehensively.

## The Key Context: Utah Array Geometry

This matters enormously for algorithm choice. The Kilosort4 paper explicitly notes that some data cannot be drift-corrected effectively due to either lacking a well-defined geometry (tetrodes) or due to the vertical spacing between electrodes being too high (more than 40 μm), and that this consideration also applies to data from single electrodes such as in a Utah array. With 400 μm inter-electrode spacing, there is essentially no meaningful spatial overlap of the same neuron's signal across neighboring electrodes — each channel is effectively an independent single-channel recording. This is the defining constraint that shapes which algorithms will actually help you and which will be wasted effort.

---

## OFS v3 Built-in Algorithms

A study by Dann et al. (2019) systematically compared the OFS clustering algorithms — Template Matching, K-Means, Valley Seeking, Standard E-M, and T-Distribution E-M — using both experimental and artificial data with known ground truth. Here's how they break down:

**Valley Seeking** is a nonparametric density-based method that works by counting neighbors within a Parzen-window radius in PCA feature space, then finding cluster boundaries at density valleys. The study concluded that Valley Seeking produces the most accurate results when exclusion of artifacts as unsorted events is important, because it naturally leaves ambiguous waveforms unsorted rather than forcing them into a cluster. The tradeoff is that it's sensitive to the Parzen multiplier parameter — decreasing it produces more clusters, increasing it produces fewer. It can also be slow on channels with very high spike counts.

**K-Means** is a standard centroid-based partitioning algorithm. It was found to be a better option when artifact exclusion is less important — i.e., on cleaner data. It's fast and deterministic given a fixed number of clusters, but it requires you to specify (or let OFS guess) the number of units, assumes roughly spherical clusters, and assigns every waveform to some unit, which can be problematic with noisy data.

**T-Distribution E-M** is OFS's most sophisticated automatic algorithm. It models clusters as multivariate t-distributions rather than Gaussians, making it more robust to outliers than Standard E-M. It can obey a specified Waveform Limit and automatically perform "Following Sort" actions of assigning unsorted waveforms to the nearest cluster and removing outliers, which makes it practical for channels with millions of spikes. It automatically determines the number of clusters. The downside is it's slower and requires more iterations to converge.

**Standard E-M** assumes Gaussian-shaped clusters, which makes it faster to converge than T-Dist E-M but more susceptible to outliers pulling cluster shapes. Standard E-M generally performs better with a smaller number of max iterations than T-Distribution E-M requires.

**Template Matching** works by correlating waveforms against defined templates. It's excellent for stable recordings where you have good prior template shapes (e.g., from a previous sort), but it's not a discovery algorithm — it can't find new units you haven't defined.

**Overall strengths of OFS for Utah arrays:** It was literally designed for this kind of single-channel, electrode-per-electrode workflow. The batch mode, GUI-based manual curation, scan-through-parameters approach, and per-channel template system are all well-suited. The study found high variability in sorting results across different algorithms, with variability increasing as unit shape similarity increased, which underscores the value of OFS's interactive curation tools.

**Overall weaknesses:** All OFS algorithms operate strictly on a per-channel basis with no cross-channel information. They rely on PCA or hand-picked features (voltage slices, peak, valley, etc.) for dimensionality reduction, which can miss discriminative features that wavelet-based or learned representations would capture. There is no drift tracking built into OFS v3. And the algorithms are all relatively classical — no template learning, no overlap deconvolution (that's an OFS v4 feature), and no modern nonlinear clustering.

---

## Modern Alternatives and How They Fare on Utah Arrays

**Kilosort (1–4)** is the dominant modern spike sorter, but it was built for dense probes. Its core strengths — template-matching integrated with spike detection, GPU-accelerated matching pursuit for resolving overlapping spikes, and drift correction — are designed for situations where a single neuron appears on multiple nearby channels. The authors recommend that Kilosort2 might be a better algorithm for Utah array data, because it performs drift tracking without requiring an explicit channel geometry. You can run Kilosort on Utah array data by treating each channel independently or in small groups, but you lose the multi-channel template advantage that makes Kilosort powerful. Kilosort4 outperformed all other algorithms in benchmarks, finding 80–90% of units versus around 50% for the nearest competitor (IronClust), but these benchmarks were on dense probes with significant spatial overlap — a fundamentally different regime from Utah arrays.

**MountainSort4/5** uses an ISO-SPLIT clustering algorithm (a nonparametric test for unimodality) that automatically determines the number of clusters without assuming cluster shapes. It works on a per-channel or per-neighborhood basis. In SpikeInterface benchmarks, it was excluded from the high-channel-count analysis as it was considered alongside WaveClus as designed for lower channel count probes. This actually makes it more naturally suited to Utah array data than Kilosort. It's fully automatic, handles non-Gaussian cluster shapes well, and doesn't require a GPU. The weakness is that MountainSort processes data in fixed-duration blocks and applies a merging procedure that does not explicitly account for drift-induced shifts in waveforms, so it can struggle with nonstationarity over long recordings.

**SpyKING CIRCUS** uses a template-matching approach with dictionary learning. It achieved similar accuracy to Kilosort on validated datasets (4.4% error rate versus 4.2%) while using less memory and scaling well via MPI parallelization across CPU cores. It could run on recordings with thousands of electrodes where Kilosort could not scale up. However, SpyKING CIRCUS lacks any drift compensation mechanism, which matters for chronic Utah array recordings where electrode-tissue interface changes over sessions. Like Kilosort, its multi-channel template approach provides less benefit when electrodes are 400 μm apart.

**Wave_clus** uses wavelet decomposition for feature extraction combined with superparamagnetic clustering. It is designed for low channel count probes, which makes it conceptually well-suited for Utah array per-channel sorting. An updated version achieved significantly fewer total errors than Kilosort, SpyKING CIRCUS, and MountainSort on simulated single-channel data, primarily through better automatic selection of the number of clusters and better handling of varying noise levels. The wavelet features can capture discriminative waveform characteristics that PCA misses. The main weakness is speed — it's MATLAB-based and not GPU-accelerated, so batch processing 96 channels is slow.

**SpikeSift** (newer, 2025) is specifically designed for computational efficiency. It achieved a 10-fold speed advantage over Kilosort, MountainSort, and SpyKING CIRCUS on a single CPU core, despite the others using GPU acceleration or multithreading. It also maintained reliable performance across both gradual and abrupt drift scenarios through a segmentation-based framework that enables local adaptation without relying on accurate drift trajectories. This could be very attractive for Utah array batch processing given your speed concerns.

## Practical Recommendation for Your Utah Array Workflow

For 400 μm spacing, the multi-channel spatial advantages of Kilosort/SpyKING CIRCUS are largely irrelevant. Your choice comes down to:

If you need to **stay in OFS** (for publication continuity, lab standards, etc.), T-Dist E-M with a waveform limit and parameter scanning is your best automatic option, with Valley Seeking as a good alternative when you want conservative sorting that leaves ambiguous spikes unsorted. Use the scan feature to systematically explore parameter space per channel.

If you're open to **switching or supplementing**, Wave_clus or MountainSort5 are the most natural fits for per-channel Utah array data. Wave_clus in particular excels at exactly this use case — single-channel, automatic cluster number determination, wavelet features that can discriminate units PCA misses. You could run these through SpikeInterface to compare results directly.

If **speed is paramount** (which it sounds like from your batch processing questions), look at SpikeSift or Kilosort2 (running per-channel). Kilosort2 in particular is fast and handles nonstationarity better than OFS's algorithms, even on single-channel data.
