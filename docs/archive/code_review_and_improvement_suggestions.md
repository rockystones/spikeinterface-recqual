## Analysis: What the Code Does

The pipeline has four stages: (1) load sorted spike waveform `.mat` files from two Utah arrays, extract per-channel unit counts and max peak-to-peak amplitudes; (2) rearrange data by array and coating type (TNP vs TNP L1), computing yield and amplitude metrics over time; (3) generate heatmaps of unit counts and amplitudes mapped to the 10×10 electrode grid; (4) import EIS impedance data, compile 1 kHz impedance over time, and correlate impedance with unit yield/amplitude.

---

## Key Problems

**1. Three nearly identical 600+ line scripts with no shared code.** Every time you add a new recording session, you duplicate the entire script and change the file list. This is the single biggest maintainability problem — bugs fixed in one version don't propagate, and the commented-out "Bin by month" section at the bottom references `SN1473`/`SN1496` (from a previous animal?) that doesn't apply to Rocky at all.

**2. Hardcoded everything.** File paths, array serial numbers, coating maps, channel maps, implant date, exclusion thresholds, figure sizes — all embedded directly in the script body. Changing any parameter means editing the script itself.

**3. The `eval(strcat('CMP',num2str(array_SN(i))))` pattern** is fragile and dangerous. It dynamically constructs variable names from the workspace, which breaks if those variables (`CMP4377`, `CMP4419`) aren't pre-loaded. These electrode map variables are never defined anywhere in the scripts you uploaded — the code will crash at this line unless you've run something else first.

**4. Redundant computation inside loops.** Inside the channel plotting loop, `temp_imp2=Compiled_unit_data.Arranged_Data.(Array_SN).num_units` is re-assigned on every iteration of `chan_indx` (96 times) even though it doesn't depend on the channel.

**5. The `num_units_by_type` cell array uses hard-coded row indices** (`{1,2}` for TNP, `{2,2}` for TNP L1) that silently produce wrong results if the coating assignment changes. Since both arrays are uniformly coated (SN4377 is all coating type 2, SN4419 is all type 3), the "by type" separation doesn't actually filter anything — every channel on a given array maps to the same coating code.

**6. Memory management is ad hoc.** You call `clear sorted_unitdata` and `fclose('all')` manually but still accumulate the full `Compiled_unit_data` struct in memory with all waveforms across all sessions.

**7. No error handling.** If a `.mat` file is missing a channel field or has unexpected dimensions, the script crashes with no diagnostic message.

**8. The impedance remapping uses a different channel map** (`Blackrock_TDT_to_channel_map`) than the spike data remapping (`Blackrock_elec_to_channel_map`), which is correct since impedance comes from TDT while spikes come from Blackrock — but there's no comment or assertion verifying that the right map is being applied to the right data stream.

**9. Figures are created but never assigned axis handles consistently**, making it hard to customize individual subplots. The `heatmap` function in MATLAB doesn't support `caxis` directly (it uses `ColorLimits` property), so some of those `caxis` calls may silently fail depending on your MATLAB version.

This is a really important question, and the short answer is: it would severely degrade sorting performance for most sorters, and in some cases produce misleading results. Let me walk through why, because the failure modes are different depending on which sorting algorithm you're using.

**What the .nev actually contains:** The Blackrock system does real-time threshold crossing detection on the hardware, then saves a short snippet (typically 48 samples — 1.6 ms at 30 kHz) around each detected event, along with a timestamp and the online-assigned unit label. The continuous signal between spikes is discarded. So if you zero-pad these snippets back into a "continuous" trace, you get something like brief waveform islands floating in a sea of zeros.

**How this breaks each sorter's assumptions:**

*Template-matching sorters (Kilosort4, SpyKING CIRCUS)* operate on the continuous trace directly. They slide learned templates across the data and look for matches, handling overlapping spikes by subtracting detected spikes from the residual and re-scanning. With zero-padded snippet data, the template matching itself might still find isolated spikes, but several things go wrong. The noise covariance estimate — which every template matcher uses to whiten the data and set detection thresholds — would be computed from a signal that's mostly zeros. This produces a wildly wrong noise model: the estimated noise floor drops to near zero, so the detection threshold (expressed in noise standard deviations) effectively becomes infinitely sensitive during the zero regions and poorly calibrated during the snippet regions. Kilosort4 specifically estimates drift and spatial templates from continuous data statistics, both of which become meaningless when the "background" is artificial silence.

*Clustering-based sorters (MountainSort5, Tridesclous)* first detect spikes via threshold crossing, then extract features (PCA, wavelet coefficients) from the detected snippets, and finally cluster in feature space. These are the least damaged by the zero-padding approach, because the detection step would re-find the spikes in the snippets (they're above threshold), and the waveform shapes within the snippets are real. However, there are still problems. The threshold is typically set as a multiple of the estimated noise standard deviation (e.g., `median(|x|) / 0.6745`). With a mostly-zero signal, this estimate collapses, and you'll detect every tiny fluctuation at snippet boundaries as a "spike." You'd also lose any spikes that the Blackrock hardware missed in the first place — since those events never made it into the .nev, they can't be recovered.

*The preprocessing chain itself breaks down.* Bandpass filtering a zero-padded signal produces ringing artifacts at every snippet onset and offset — the filter's impulse response bleeds energy from the abrupt waveform-to-zero transitions in both directions. Common reference subtraction becomes meaningless when most channels are zero at any given moment. Whitening, which depends on the cross-channel noise covariance, would learn a degenerate covariance matrix.

**The more subtle problems:**

Overlapping spikes are completely invisible. If two neurons fire within ~1 ms of each other, the Blackrock hardware captures one composite snippet. A good offline sorter working from continuous data can decompose overlapping waveforms (Kilosort4 and SpyKING CIRCUS are specifically designed for this). With snippet data, that decomposition is impossible because you only have the single pre-extracted window — you've lost the ability to see the overlap in context.

Firing rate and ISI statistics get distorted. Any quality metric that depends on the relationship between spike times and the total recording duration (firing rate, presence ratio, burst detection) would be numerically correct in terms of timestamps, but you've eliminated the sorter's ability to discover spikes that the online detector missed. So your firing rates are biased low by exactly the false-negative rate of the Blackrock hardware detector, which can be substantial for low-amplitude units.

Drift tracking fails entirely. Modern sorters track slow changes in waveform shape and amplitude over the course of a recording (tissue settling, electrode drift). They do this by analyzing how templates evolve across sequential batches of continuous data. Zero-padded snippets provide no temporal continuity for this estimation.

**When snippet-only sorting is actually reasonable:**

If all you have is the .nev and you want to *re-cluster* the already-detected spikes (perhaps because you disagree with the online sorter's unit assignments), the correct approach is not to fake a continuous recording. Many dates also have both AnalogHeadstage and DigitalHeadstage recordings; the deduplication logic keeps only the DigitalHeadstage version when both exist (configurable via `preferred_headstage`). Files are then sorted chronologically within each array group.

**Stage 3** compiles the `num_units` and `max_amp` matrices that Stage 1 already computed into a clean `Arranged` struct indexed by array label. It also computes `max_amp_nan` (zeros replaced with NaN for "active channels only" statistics) and per-session channel yield.

**Stages 4–5** produce the comparison plots: errorbar plots of mean ± SEM for unit count, max amplitude (all channels and active-only), and channel yield over time, plus per-channel spaghetti plots with the mean overlaid.

**Stage 6** finds recording dates that exist in *both* the Anterior and Posterior datasets and runs the comparison only on those matched time points. This is important because your two arrays don't have identical recording schedules — the Anterior list has some dates the Posterior doesn't and vice versa. The difference plot (L1 minus Ctrl) gives you a quick visual of which coating performs better at each time point.

**Stage 7** bins by approximate month (30-day windows) and pools all sessions within each month for smoother longitudinal trends.

**Stage 8** runs Wilcoxon rank-sum tests at each matched time point, comparing the 96-channel distributions between arrays. This is non-parametric and unpaired, which is appropriate since the two arrays are in different cortical locations.

**One thing you need to set:** the `Rocky_Implant_date` at the top. I used `2017-09-20` as a placeholder since your earliest recording is `2017-09-21`, but adjust this to the actual surgery date. This shifts all the "days post implant" values on your x-axes.

**One thing to watch for:** the file `Rocky_Anterior_2023-08-011_Baseline_DigitalHeadstage-01.wfexp.mat` has what looks like a typo in the date (`08-011` instead of `08-11`). The date parser will fail on this and issue a warning — you may want to rename that file before running.
